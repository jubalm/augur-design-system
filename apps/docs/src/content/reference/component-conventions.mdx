Every component in `@augur/design-system` follows the same ownership model: Augur owns the API, styling, documentation, and verification contract even when a familiar implementation shape comes from shadcn or a primitive library.

## Layering

Components consume semantic roles and shared foundations. They do not own system-wide color, focus, motion, spacing, or geometry rules unless a component has a concrete exception.

```text
Foundations → Tokens → Primitives → Components → Patterns → Products
```

Use native elements first. Introduce a primitive such as Radix only when the interaction model requires behavior that native elements do not provide cleanly.

## Visual contract

Component CSS uses semantic role custom properties rather than raw color values or generated color primitives directly. Shared layout and interaction decisions live in:

- [Layout and geometry](/foundations/layout-geometry)
- [Interaction](/foundations/interaction)
- [Color](/foundations/color)
- [Theming](/foundations/theming)

Do not duplicate those rules in every component page. A component page should explain how they apply and document exceptions.

## API conventions

- Public exports use PascalCase and are re-exported from the package entry.
- Internal file organization is not public API.
- Prefer small string-union variant/size props over open-ended visual props.
- Composition parts follow real semantic elements where possible.
- React 19 refs are passed directly; avoid `forwardRef` unless a concrete compatibility requirement appears.
- `className` extends the component rather than replacing its contract.
- Product workflow, validation policy, and domain state stay outside the design-system component.

## Documentation contract

Each component page must help a consumer make a correct decision, not merely enumerate props.

Required core sections:

```text
When to use
When not to use
Variants
Sizes
States
Accessibility
API
```

The documentation contract may evolve toward anatomy, adaptive behavior, related components/patterns, and verification where those sections add real decision value. Sections that do not apply should be explicitly treated as not applicable rather than filled with speculative variants or states.

Live examples must import the real package component. Displayed code should come from the same example source so rendering and sample text cannot drift independently.

## Testing expectations

A component change should prove the parts relevant to its contract:

- package/unit tests for exports and class/API behavior;
- repository interaction tests for keyboard, state, semantics, and axe findings;
- docs/browser fixtures for rendered geometry and theme behavior when visuals change;
- source-registry generation/consumer checks when the registry item changes;
- maintainer visual review where issue #53 or a successor acceptance gate applies.

Passing deterministic tests does not establish visual acceptance.

## Registry distribution

The source registry is generated from canonical repository sources. Registry output must not become a hand-maintained second implementation.

The base `augur-theme` item carries the shared system contract; component and pattern items compose on top of it. Consumers should pin verified refs for reproducibility.

## Adding or changing a component

1. Confirm the component belongs in the Components layer rather than a Pattern or product surface.
2. Reuse the maintained foundations; do not invent local visual rules to complete the design.
3. Define the smallest API that serves the concrete use case.
4. Implement with native semantics or an appropriate primitive.
5. Document when to use it, when not to use it, behavior, accessibility, and API.
6. Add real examples and the relevant deterministic/browser verification.
7. Verify registry output if the component is externally consumable.
8. Escalate unresolved design decisions instead of silently creating new system rules.
