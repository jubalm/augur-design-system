This page is the contributor-facing working guide. Canonical repository rules remain in `AGENTS.md`, `ARCHITECTURE.md`, `DESIGN.md`, and the repository README.

## Authority

Use this order when sources appear to disagree:

1. `DESIGN.md` — adopted design values representable by the pinned schema.
2. Generated tokens/theme output — derived artifacts; never independent sources of truth.
3. Maintained foundation guidance and implementation — concepts that do not fit the schema cleanly.
4. Component/pattern documentation — usage and composition contracts.
5. Upstream brand material, issues, fixtures, and history — evidence and provenance; they do not silently override maintained decisions.

Do not revive superseded proposal language from historical records.

## Boundaries

```text
Foundations → Tokens → Primitives → Components → Patterns → Products
```

- `packages/design-system` is the reusable system package.
- `apps/docs` consumes the package; the package never imports docs code.
- Tokens do not know about components.
- Components use semantic roles rather than raw design values.
- Patterns compose reusable components/structure without taking on product workflow.
- Product-specific logic stays outside the design system.

## Artwork

Production brand artwork may only come from verified supplied masters. Do not trace, redraw, reconstruct, recolor, or approximate missing logo assets. Follow the maintained [Brand identity](/foundations/identity) page and `resources/brand/PROVENANCE.md`.

## Workflow

1. Read the issue, its dependencies, and current repository authority before editing.
2. Keep the change inside the requested layer and scope.
3. Reuse existing foundations before proposing new design rules.
4. Implement and document the smallest coherent change.
5. Run the checks relevant to the changed surface.
6. For visual changes, inspect both themes and relevant viewport sizes; deterministic tests are not visual acceptance.
7. Open a PR with outcome, affected surfaces, observed verification, and remaining limitations.
8. Leave a handoff that makes ownership, blockers, and unresolved decisions explicit.

## Verification

Use the repository scripts and package/docs checks as the executable contract. Common categories include:

- schema/design validation;
- lint and typecheck;
- workspace boundary checks;
- unit/component/accessibility tests;
- token regeneration parity;
- docs build and Markdown endpoint verification;
- browser/fixture checks for rendered behavior;
- registry generation and standalone consumer verification when distribution changes.

The exact commands are maintained in the repository README, package scripts, and CI workflow. Prefer those canonical executable definitions over copying command inventories into design guidance pages.

## Documentation changes

Documentation is part of the system contract. When changing it:

- keep one primary home for each durable rule;
- prefer moving/reworking existing guidance over adding another overlapping page;
- remove stale project-state snapshots;
- keep historical evidence accessible without placing it in the normal learning path;
- preserve the single content/navigation model, clean Markdown endpoints, and `llms.txt` generation.

## Maintainer boundaries

Merge, release publication, public deployment, DNS, licensing, repository transfer, and final visual acceptance remain explicit maintainer actions unless authority has been delegated for the specific task.
